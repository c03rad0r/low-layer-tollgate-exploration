## Question

Before building a frame gate into the link module, confirm two things:

1. nft `netdev` ingress can match EtherType `0x2121` and drop it.
2. An authorised-MAC set can admit and revoke individual senders.

The captive-portal question — whether `ndsctl` deauthorisation stops `0x2121` —
is a different experiment and is still blocked on a real AP.

## Setup

```sh
harness/ethernet-lab/run-frame-gate.sh 200
```

The script builds a small Alpine image and runs `frame-gate-test.py` in a
container with `NET_ADMIN` and `NET_RAW`, `--network none`. Inside:

- `veth` pair `v0` (sender) ↔ `v1` (receiver);
- `netdev` ingress chain on `v1`;
- an `authorised_macs` set of type `ether_addr`;
- rules:

```
ether type 0x2121 ether saddr @authorised_macs counter accept
ether type 0x2121 counter drop
```

IPv4/UDP delivery is the control: the same chain can drop `ether type 0x0800`,
which is observable at a UDP socket. `0x2121` has no kernel handler, so its
verdict is observed in nft counters.

## The methodological finding

The first version of the test counted frames with an **AF_PACKET** socket on the
receive side. It reported 200/200 received even when nft's counter showed 200
dropped. Packet taps run **before** the netdev ingress hook, so AF_PACKET sees
traffic that the firewall has already dropped.

The corrected test uses nft counters for the `0x2121` verdict, and a handled
EtherType (IPv4/UDP) to prove that the same chain blocks real delivery. Both
are needed: counters alone would not prove the hook is effective, and delivery
alone is impossible for `0x2121` because nothing in the kernel handles it.

This trap is recorded in `harness/ethernet-lab/README.md` so no later experiment
repeats it.

## Interpretation

nft `netdev` ingress matches `0x2121`, honours an `ether_addr` set, and applies
the verdict on the real receive path. The rule shape in `docs/0006` is
implementable as written.

It does **not** answer the captive-portal question. `ndsctl` installs IP-family
rules; whether it drops `0x2121` depends on the portal's implementation and
needs a real AP. It also does not measure drop cost at line rate (Exp E2), and
it does not make MACs trustworthy: a sender can put any source MAC on the wire.
This remains **rate/abuse control, not authorisation**.
