## Question

Does the gate behave the same over the Ethernet transport, with no static peer
addresses? Specifically: can neighbours discover each other by beacon, is
metering still at the FMP frame boundary, and does runtime admission hold a
denied peer out?

## Setup

Two nodes, one Docker bridge, one Ethernet transport each:

```yaml
transports:
  ethernet:
    interface: "eth0"
    ethertype: 0x2121
    announce: true
    auto_connect: true
    accept_connections: true
    beacon_interval_secs: 10
```

There are no `peers:` entries and no addresses. Containers run with
`NET_ADMIN` and `NET_RAW`. FIPS reports MTU 1497 (1500 minus the 3-byte
frame header).

```sh
harness/exp-eth/run-eth.sh
```

Three clean runs, fresh compose project each time.

## Interpretation

1. **Ethernet discovery is fast and address-free.** The first beacon arrived
   inside a second in every run, well before the 10 s steady-state interval.
   No peer entries or addresses are needed.
2. **The counter boundary is unchanged.** Metering reads the same FMP frame
   bytes; the 3-byte Ethernet frame header and 14-byte MAC header are outside
   the transport payload. This is the same boundary as UDP/TCP.
3. **Runtime admission works on Ethernet.** After `admission deny` and a
   disconnect, the peer never reappeared in the 4 s window, despite beacons.
4. **Re-admission is beacon-paced.** ~6.0 s, versus ~2.7–3.2 s on UDP/TCP where
   the peer dials directly. That is a transport property, not a gate cost: the
   gate does no waiting.
5. **The transport is a policy scope, not new gate code.** The same sidecar
   `snapshot`/`delta` and `set_admission` calls were used unchanged.

## Caveats

- One L2 segment, two nodes. The chain result is separate
  (`PE-2026-11-03-pause-ethernet.md`).
- Docker bridge, not a real switch or Wi-Fi. The Exp E `nft` half covers the
  captive-portal question separately.
- Ethernet frames are flooded on the bridge; this says nothing about a
  switched production LAN's isolation.
- No payment traffic.
